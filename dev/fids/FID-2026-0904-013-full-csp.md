## Summary

FID-012 shipped only the minimal CSP fragment (`frame-ancestors 'none'`) and
explicitly deferred the full-surface policy as untested follow-up work. This
FID designs and ships the real Content-Security-Policy: script/style
allowlists, the Supabase/YouTube/GitHub image and connection origins, and a
violation-report endpoint for staged enforcement. The central design decision
is **hash-free host allowlisting, not nonces**: the official Next.js guide
confirms nonce-based CSP requires dynamic rendering for every page ("Static
optimization and Incremental Static Regeneration (ISR) are disabled") — which
would silently undo FID-012's entire ISR completion (home + 7 listings +
detail routes all edge-cached, verified `X-Vercel-Cache: HIT` in
production). A host-allowlist CSP is fully compatible with prerendered
pages: the header is a constant, set once in `next.config.mjs`.

## Evidence (RED)

All evidence from tool output, 2026-09-04.

**E1 — current policy is two directives** (`next.config.mjs`):
`Content-Security-Policy: frame-ancestors 'none'`. No `script-src`, no
`img-src`, no `connect-src` — browsers fall back to `default-src`-absent
"allow everything" behavior for every unlisted directive. Any injected
`<script src>` executes today.

**E2 — actual client-side surface, grepped from the repo:**

- No in-tree analytics/ads/error-trackers: the only `use client` fetches are
  CommentSection (`/api/comments`, `/api/auth/me`) and the auth flows.
- Client-side **Supabase auth is real**: `lib/supabase/client.ts` calls
  `createClient(getSupabaseUrl(), …)` in the browser → runtime fetches to
  `https://xunlxdvlhfxokxjnxgrp.supabase.co/auth/v1/...` (sign-in/sign-up
  from `app/(auth)`, session exchange from `app/api/auth/session` consumers).
  Any `connect-src` without the project host **breaks login sitewide**.
- One iframe only: `app/watch/[videoId]/page.tsx` →
  `https://www.youtube-nocookie.com/embed/…` (frame-src).
- Zero `style={{…}}` inline-style objects in `app/` + `components/` (grep
  count 0) — but Next.js itself emits inline `style` attributes on hydrated
  elements, so `style-src 'self'` without `'unsafe-inline'` is not assumed
  safe without a report-only round.
- Fonts self-hosted via `next/font` (`config/fonts.ts`) — no Google Fonts
  runtime fetch; the CSS is inlined into the stylesheet.
- Fallback images are local paths (`config/type-visuals.ts`: `/rss.jpg`,
  `/reddit.jpg`, …), no data: URIs in code.

**E3 — actual image hosts in the content table** (live DB probe, 773 rows
sampled): `opengraph.githubassets.com` (trendshift + opensource cards) and
`i.ytimg.com` (youtube). `img-src` needs exactly `'self'` + those two hosts
(+ `data:` reserved for sanitizer-passed inline images).

**E4 — publisher article images are an unknown-population problem**: the
sanitize-html contract (`lib/fetchers/article.ts`) allows `<img src>` with
http/https/data schemes. Article bodies may reference ANY publisher host. A
closed `img-src` allowlist cannot be known in advance → this is the exact
use case for the staged `Content-Security-Policy-Report-Only` round: collect
2–7 days of real violations, then add the observed legitimate hosts before
enforcement. (A counter-proposal — stripping article images at fetch time —
was rejected: it degrades the reader for a policy problem solvable with
observation, and violates the "include the same info the website does"
operator requirement from FID-2026-0904-009.)

**E5 — nonce/ISR conflict (official docs, nextjs.org CSP guide, retrieved
2026-09-04)**: "When you use nonces in your CSP, all pages must be dynamically
rendered… Static optimization and Incremental Static Regeneration (ISR) are
disabled… Pages cannot be cached by CDNs without additional configuration."
The guide's no-nonce alternative is exactly `next.config.js headers()`.
Experimental SRI (hash-based, static-compatible) exists but is flagged
experimental — recorded as a deferred upgrade, not shipped on a production
site.

**E6 — current report surface**: none. No endpoint exists to receive
`report-uri`/`report-to` violations, so today there is no way to observe
what a stricter policy would break.

## Proposed Solution (GREEN)

### 1. Policy (the actual header)

```
default-src 'self';
base-uri 'self';
connect-src 'self' https://xunlxdvlhfxokxjnxgrp.supabase.co;
default-src fallback covered above;
font-src 'self';
form-action 'self';
frame-ancestors 'none';
frame-src https://www.youtube-nocookie.com;
img-src 'self' data: https://i.ytimg.com https://opengraph.githubassets.com;
media-src 'none';
object-src 'none';
script-src 'self' 'unsafe-inline' 'unsafe-eval' (dev only);
style-src 'self' 'unsafe-inline';
upgrade-insecure-requests;
report-uri /api/csp-report (report-only phase) / report-to on enforce
```

Directive-by-directive rationale:

- **`script-src 'self' 'unsafe-inline'`** — the honest trade-off. `'self'`
  blocks every injected third-party script (the XSS kill-shot: an attacker's
  `<script src="https://evil.com">` cannot load; `<script>alert()</script>`
  inline is allowed, which the sanitizer contract already covers — no raw
  third-party HTML is ever rendered, article bodies strip script/style/iframe
  wholesale, E2). Dropping `'unsafe-inline'` requires nonces (kills ISR, E5)
  or experimental SRI (E5) — neither is the right trade on day 2 of a
  content site whose pages are 100% framework-generated. Recorded honestly
  in the FID rather than smuggled as if it were stricter than it is.
- **`style-src 'self' 'unsafe-inline'`** — Next emits inline `style`
  attributes during hydration; blocking them breaks rendering. Revisit with
  SRI upgrade.
- **`connect-src 'self' <project-ref>.supabase.co`** — the client Supabase
  auth surface (E2). Without it, register/login/session-break. `'self'`
  covers `/api/comments` and `/api/auth/*`.
- **`img-src 'self' data: https://i.ytimg.com https://opengraph.githubassets.com`**
  — E3's DB-probed hosts, plus the sanitizer's data-scheme allowance. Any
  additional article-image host discovered in the report-only round gets
  added here *before* enforcement (E4).
- **`frame-src https://www.youtube-nocookie.com`** — the watch embed, the
  only iframe in the app.
- **`font-src 'self'`** — next/font self-hosts (E2).
- **`object-src 'none'; media-src 'none'; base-uri 'self'; form-action
  'self'; frame-ancestors 'none'; upgrade-insecure-requests`** — hardening
  defaults; `frame-ancestors` preserves FID-012's clickjacking defense.
- **`default-src 'self'`** — the catch-all: any future unlisted directive
  denies by default instead of allowing.
- No `report-to` group configuration in phase 1 (the endpoint handles
  `application/csp-report` and `application/reports+json` shapes without it).

### 2. Staged rollout (the actual safety mechanism)

- **Phase A (this FID, this deploy): Report-Only.** Next 16 supports
  `Content-Security-Policy-Report-Only` via `next.config.mjs` `headers()`.
  The header ships sitewide INCLUDING in production; browsers evaluate it,
  report every violation to `/api/csp-report`, and block nothing. Users see
  zero difference; we learn the truth about article-image hosts and any
  Next internals I could not grep for.
- **Phase B (gated on evidence): Enforcement.** Flip the same policy from
  the Report-Only header to `Content-Security-Policy` (add `report-uri`
  alongside), after: (a) ≥3 days of report traffic reviewed, (b) zero
  violations from first-party origins in the trailing 48h, (c) article-image
  hosts observed in reports added to `img-src` if legitimate, blocked hosts
  left out. Phase B is its own commit + production verification round; it is
  NOT auto-flipped by time.
- The rollout switch lives in ONE place (Law 13): a `CSP_REPORT_ONLY` const
  at the top of `next.config.mjs` choosing which header name the policy is
  served under. Phase B is a one-line change.

### 3. Violation collector — `app/api/csp-report/route.ts`

- `POST`, accepts `application/csp-report` (classic) and
  `application/reports+json` (Reporting API), responds `204 No Content`.
- Logs one line per violation: `violated-directive`, `blocked-uri`,
  `source-file:line`, `disposition` (so report-only vs enforce is visible in
  logs), sampled (log every report in phase A; volume is low on this site —
  add sampling later only if it grows).
- Caps body size (8 KB), never stores, never reflects — a logging sink only,
  no auth (browsers send these pre-auth by spec), no PII beyond what the
  browser itself puts in the report.
- Registered in robots as part of `/api/` (already disallowed by FID-012's
  robots.ts).

### 4. Rollback plan

- **Header-level rollback**: revert the `headers()` block in
  `next.config.mjs` (one hunk, one file) → deploy. Report-Only phase cannot
  break the site by definition (browsers only report); enforcement-phase
  rollback is the same revert with the header removed entirely — Vercel
  serves no CSP within ~2 minutes of the deploy finishing.
- **Endpoint rollback**: `app/api/csp-report/route.ts` is additive; deleting
  the file removes the endpoint. A dead `report-uri` target only produces
  failed browser fetches (silent, no user impact).
- **Worst-case breakage during phase B** (a missing legit host in
  `img-src`/`connect-src`): symptom is visible breakage + matching violation
  reports in logs; the revert is the same single-hunk header removal. No
  database, schema, or data rollback is ever implicated — CSP is a pure
  response-header concern.
- Vercel-specific note: headers() changes are live after the deploy completes;
  there is no CDN purge step needed beyond that.

### 5. Deferred (explicitly NOT in this FID)

- Nonce/'strict-dynamic' strict CSP — incompatible with the site's
  ISR-cached page model (E5); would reverse FID-012.
- Experimental SRI upgrade — the future path to drop `'unsafe-inline'` from
  script-src while staying static; track the Next.js flag stabilizing first.
- report-to/Reporting-API group registration — the classic endpoint covers
  phase A; group config adds moving parts without changing what we learn.
- Subresource allowlists for future third-party embeds (analytics, etc.) —
  none exist today (E2); add when one is adopted, not before.
